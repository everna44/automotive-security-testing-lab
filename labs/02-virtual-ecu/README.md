# Lab 02 — 최소 소프트웨어 가상 ECU

Python과 python-can의 SocketCAN 백엔드로 읽기 요청만 처리합니다. 실제 실행 대상은 Linux의 `vcan0`이며 실제 차량·물리 ECU 시험이 아닙니다. UDS 또는 ISO-TP 구현이 아닌 이 실습의 독자적인 단일 프레임 규격입니다.

## 통신 규격

표준 11비트 Classical CAN을 사용합니다.

| 항목 | 정의 |
|---|---|
| 요청 / 응답 ID | `0x120` / `0x121` |
| 요청 Payload | `[SEQ, CMD, VALUE_H, VALUE_L]`, 정확히 4바이트 |
| 응답 Payload | `[SEQ, STATUS, CURRENT_H, CURRENT_L]`, 정확히 4바이트 |
| 정수 형식 | unsigned 16-bit big-endian |
| 초기 setting_value | 50 (`0x0032`) |
| 지원 명령 | 읽기 `CMD=0x01`, 요청 VALUE=`0x0000` |
| 성공 STATUS | `0x00`, SEQ는 요청 값을 그대로 반환 |
| 테스트 요청 / 기대 응답 | `10 01 00 00` / `10 00 00 32` |

ECU는 다른 ID, 길이, 명령, VALUE, 확장 프레임, CAN FD, RTR, 오류 프레임을 무시합니다. 상태를 변경하는 경로는 없습니다. 상세 오류 응답과 쓰기 명령은 다음 단계의 범위입니다.

## 실행 절차

저장소 루트에서 실행합니다. 전제 조건은 Ubuntu 24.04, Python 3.12와 활성화된 `vcan0`입니다. 인터페이스 준비에는 관리자 권한이 필요하며 [Lab 01 절차](../01-can-network-analysis/README.md#1-가상-can-인터페이스-준비)를 참고합니다. 이번 실행에서는 이미 활성화된 인터페이스를 사용했으며 환경을 재설정하지 않았습니다.

의존성 최초 설치는 승인을 받은 후 실행합니다. 아래 가상환경은 이번 작업에서 생성했습니다.

```bash
python3 -m venv labs/02-virtual-ecu/.venv
labs/02-virtual-ecu/.venv/bin/python -m pip install -r labs/02-virtual-ecu/requirements.txt
```

일반 사용자 권한으로 터미널 A에서 ECU를 실행합니다. `READY` 출력 후 터미널 B에서 클라이언트를 실행합니다.

```bash
labs/02-virtual-ecu/.venv/bin/python labs/02-virtual-ecu/src/ecu.py
```

```bash
labs/02-virtual-ecu/.venv/bin/python labs/02-virtual-ecu/tests/test_client.py
```

기대 결과는 다음과 같습니다. 클라이언트는 송신 후 단조 시계 기준 총 1초 동안 응답을 기다립니다. 다른 프레임을 받아도 제한 시간을 연장하지 않습니다. 일치하면 종료 코드 0, 잘못된 응답 또는 타임아웃이면 0이 아닌 코드로 종료합니다. 송신 타임아웃도 1초입니다. ECU는 `Ctrl+C`로 종료합니다. 두 프로그램 모두 `--channel` 옵션을 지원하며 기본값은 `vcan0`입니다.

```text
TX 120#10 01 00 00
RX 121#10 00 00 32
PASS: 기대 응답 일치
```

동일 인터페이스에서 다른 ECU나 응답 송신기가 동작하면 시험 판정에 영향을 줄 수 있습니다. 클라이언트는 응답 ID와 SEQ를 포함한 전체 Payload를 대조하지만 송신 프로그램의 신원을 인증하지 않습니다.

## 실제 실행 결과

### 기존 텍스트 로그 실행 (07:56 UTC)

2026-11-10 UTC에 Python 3.12.3, python-can 4.6.1, 활성화된 `vcan0`에서 ECU 프로세스와 별도 테스트 클라이언트를 실행했습니다. Ubuntu 24.04는 사용자 제공 환경 정보이며 이번 실행에서 OS 버전을 별도로 조회하지 않았습니다.

- 정상 요청의 기대 응답 일치를 `PASS` 로그로 확인했습니다. 기존 실행 기록에는 클라이언트 종료 코드 0으로 기재되어 있으나, 저장된 로그에는 종료 코드 자체가 없습니다.
- 잘못된 ID `0x122`, 길이 3, CMD `0x02`, VALUE `0x0001`, 확장 ID `0x120`, RTR을 각각 송신했습니다. 각 요청 후 1초 동안 응답 ID `0x121`이 관찰되지 않았습니다.
- 위 요청들 이후 정상 클라이언트로 재조회한 응답 `10 00 00 32`와 `PASS` 로그를 확인했습니다. 이 응답은 실습 규격상 값 50입니다.

기존 실행의 원본 텍스트 로그 (아래 PCAPNG와는 별도 실행):

- [ECU 송수신 로그](logs/20261110T075641242631Z/ecu.log)
- [검증 로그](logs/20261110T075641242631Z/verification.log)

비정상 입력 시험은 이번 검증용 임시 실행 코드로 수행했으며 별도 상시 테스트 도구는 추가하지 않았습니다. 저장된 테스트 클라이언트의 범위는 지정된 정상 읽기 요청 검증입니다. 이 기존 실행에 대응하는 PCAPNG와 스크린샷은 없습니다.

### 사용자 읽기 테스트 캡처 (08:33 UTC)

사용자가 가상 ECU 읽기 테스트를 직접 실행하고 저장한 증적을 검토했습니다. 이번 검토에서는 ECU나 클라이언트를 재실행하지 않았습니다.

- [PCAPNG 원본](captures/lab02-ecu-read-test.pcapng): 464바이트, SocketCAN, 인터페이스 `vcan0`, 총 2프레임. `capinfos` 및 PCAPNG 블록/SocketCAN 원시 바이트 해석으로 실제 PCAPNG 형식과 나노초 단위 저장 정밀도를 확인했습니다.
- [Wireshark 스크린샷](screenshots/01-ecu-request-response.png): PNG, 2312 × 1312. 표시 필터는 `can.id == 0x120 || can.id == 0x121`이며 두 프레임이 표시됩니다.

| 프레임 | 캡처 시각 (UTC, 2026-11-10) | CAN ID | DLC | Payload | 검증 |
|---|---|---|---|---|---|
| 1 | 08:33:22.306400575 | `0x120` | 4 | `10 01 00 00` | SEQ=`0x10`, 읽기 CMD=`0x01`, VALUE=`0x0000` |
| 2 | 08:33:22.306695150 | `0x121` | 4 | `10 00 00 32` | SEQ 일치, STATUS=`0x00`, 실습 규격상 값 50 |

두 프레임 모두 표준 11비트 Classical CAN 데이터 프레임이며 EFF/RTR/ERR 플래그는 꺼져 있습니다. 각 SocketCAN 캡처 레코드는 16바이트이고 실제 CAN Payload는 4바이트입니다. 요청부터 응답까지 캡처 시각 차이는 `0.000294575초` (`294.575µs`)입니다. 이는 해당 두 프레임의 관찰 간격이며 ECU 내부 처리 시간이나 반복 측정 성능을 뜻하지 않습니다. 저장 정밀도가 실제 시계 정확도를 보장하지는 않습니다.

스크린샷의 요청 ID·DLC·Payload, 두 프레임 순서와 상대 시각 `0.000294575`는 원본과 일치합니다. 첫 프레임의 화면 시각 `17:33:22.306400575 KST`는 위 UTC 시각과 같습니다. 스크린샷에서 상세하게 선택된 프레임은 요청이며, 응답 Payload는 PCAPNG 원본에서 검증했습니다.

기존 로그의 정상 요청·응답 Payload는 이번 캡처와 일치합니다. 다만 기존 로그 시작은 `07:56:41.242785 UTC`이고 캡처 시작은 `08:33:22.306400575 UTC`이므로 동일 실행의 증적으로 합치지 않습니다. 기존 ECU 로그에는 정상 교환 2회가 있지만 이번 캡처에는 1회만 있습니다. 이번 캡처만으로 기존 비정상 입력 시험이나 클라이언트의 `PASS` 출력·종료 코드를 확인할 수 없습니다. 캡처 메타데이터의 OS는 `Linux 7.0.0-42-generic`이며, 기존 사용자 제공 Ubuntu 24.04 정보와는 확인 대상이 달라 배포판 버전을 검증한 것으로 보지 않습니다.
