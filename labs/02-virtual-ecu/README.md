# Lab 02 — 최소 소프트웨어 가상 ECU

Python과 python-can의 SocketCAN 백엔드로 읽기·쓰기 요청과 상세 입력 검증을 처리합니다. 실제 실행 대상은 Linux의 `vcan0`이며 실제 차량·물리 ECU 시험이 아닙니다. UDS 또는 ISO-TP 구현이 아닌 이 실습의 독자적인 단일 프레임 규격입니다.

## 통신 규격

표준 11비트 Classical CAN을 사용합니다.

| 항목 | 정의 |
|---|---|
| 요청 / 응답 ID | `0x120` / `0x121` |
| 요청 Payload | `[SEQ, CMD, VALUE_H, VALUE_L]`, 정확히 4바이트 |
| 응답 Payload | `[SEQ, STATUS, CURRENT_H, CURRENT_L]`, 정확히 4바이트 |
| 정수 형식 | unsigned 16-bit big-endian |
| 초기 setting_value | 50 (`0x0032`) |
| 지원 명령 | 읽기 `CMD=0x01` (VALUE=0), 쓰기 `CMD=0x02` (VALUE=0~100) |
| 성공 STATUS | `0x00`, SEQ는 요청 값을 그대로 반환 |
| 테스트 요청 / 기대 응답 | `10 01 00 00` / `10 00 00 32` |

정상 쓰기는 상태를 변경하고 변경된 값을 응답합니다. 잘못된 요청은 상태를 유지하며 현재 값을 응답합니다. 다른 ID, 확장 프레임, CAN FD, RTR, 오류 프레임은 응답 없이 무시합니다.

| STATUS | 의미 |
|---|---|
| `0x00` | 성공 |
| `0x01` | Payload 길이 오류 (다른 명령 오류보다 우선) |
| `0x02` | 미지원 명령 |
| `0x03` | 쓰기 값 범위 초과 |
| `0x04` | 읽기 요청 VALUE가 0이 아님 |

길이가 4바이트가 아니면 첫 바이트를 SEQ로 반환하며, 빈 Payload의 SEQ는 `0x00`입니다.

## 실행 절차

저장소 루트에서 실행합니다. 전제 조건은 Ubuntu 24.04, Python 3.12와 활성화된 `vcan0`입니다. 인터페이스 준비에는 관리자 권한이 필요하며 [Lab 01 절차](../01-can-network-analysis/README.md#1-가상-can-인터페이스-준비)를 참고합니다. 이번 실행에서는 이미 활성화된 인터페이스를 사용했으며 환경을 재설정하지 않았습니다.

의존성 최초 설치는 승인을 받은 후 실행합니다. 아래 가상환경은 이번 작업에서 생성했습니다.

```bash
python3 -m venv labs/02-virtual-ecu/.venv
labs/02-virtual-ecu/.venv/bin/python -m pip install -r labs/02-virtual-ecu/requirements.txt
```

일반 사용자 권한으로 터미널 A에서 ECU를 실행합니다. `READY` 출력 후 터미널 B에서 클라이언트를 실행합니다.

```bash
labs/02-virtual-ecu/.venv/bin/python labs/02-virtual-ecu/src/ecu.py
```

```bash
labs/02-virtual-ecu/.venv/bin/python labs/02-virtual-ecu/tests/test_client.py
```

클라이언트는 각 케이스 전에 정상 쓰기와 읽기로 상태 50을 확인합니다. 초기화 실패 시 후속 시험을 중단하고 실패로 종료합니다. 정상 읽기·쓰기, 경계 0/100, 범위 초과 101/65535, 길이 0~3·5~8, 미지원 명령, 읽기 VALUE 오류와 무시 대상 프레임을 시험합니다. 각 케이스 후 정상 읽기로 예상 상태를 확인합니다.

각 송신 뒤 단조 시계 기준 1초 동안 응답 ID `0x121`을 수집하고 예상/실제 응답, PASS/FAIL, 실패 이유를 출력합니다. 정상 응답의 SEQ·STATUS·현재 값·프레임 형식·길이와 응답 수를 검증합니다. 무응답 케이스도 1초 동안 관찰합니다. 송신 타임아웃은 1초입니다. 모든 검사가 통과하면 종료 코드 0이며 실패는 1입니다. CAN FD 무시 시험을 위해 클라이언트 소켓은 FD 수신을 허용하되 일반 요청은 Classical CAN으로 송신합니다.

ECU는 `Ctrl+C`로 종료합니다. 두 프로그램 모두 `--channel` 옵션을 지원하며 기본값은 `vcan0`입니다. 전체 시험은 약 84초가 걸립니다. 이 시험은 설정값을 변경하므로 전용 실습 인터페이스에서 실행합니다. 원본 증적을 보존하려면 재실행 로그는 `logs/` 아래 새 이름으로 저장합니다.

동일 인터페이스에서 다른 ECU나 응답 송신기가 동작하면 시험 판정에 영향을 줄 수 있습니다. 클라이언트는 응답 ID와 SEQ를 포함한 전체 Payload를 대조하지만 송신 프로그램의 신원을 인증하지 않습니다.

| 2 | 10:56:15.756878736 | `0x121` | `11 00 00 3C` | SEQ 일치, STATUS=성공, 현재 값 60: 기대 일치 |

### 실행별 증적 구분과 재현

| 증적 | 실행 시각 (2026-11-10 UTC) | 확인 범위 |
|---|---|---|
| 기존 Lab 02-2 텍스트 로그 | 10:20 시작 | 출력 수정 전 21개 케이스. 대응 캡처 없음 |
| 사용자 입력 검증 PCAPNG/스크린샷 | 10:56:15~10:56:23 | 쓰기 60, 쓰기 101 거부, 읽기 60의 3회 교환 |
| 최종 재실행 텍스트 로그 | 위 실행 메타데이터 참조 | 마지막 코드 수정 이후 21개 케이스/84개 검사. 대응 캡처 없음 |

세 실행은 합치지 않습니다. 사용자 PCAPNG는 자동 테스트의 전체 21개 케이스, PASS 출력 또는 프로세스 종료 코드를 입증하지 않습니다. 기존 읽기 전용 07:56 로그 및 08:33 캡처 역시 별도 실행입니다.

전체 시험 재현은 위 **실행 절차**대로 저장소 루트에서 일반 사용자 권한으로 ECU의 `READY`를 확인한 후 클라이언트를 실행합니다. 활성화된 전용 `vcan0`와 설치된 python-can이 필요합니다. 재실행 로그는 기존 파일을 덮어쓰지 않도록 `logs/<새 UTC 시각>-lab02-2-final/` 등 별도 디렉터리에 저장합니다. 기대 결과는 21개 케이스/84개 검사 통과와 종료 코드 0입니다.

사용자 캡처의 3회 교환을 재현하려면 같은 전제 조건에서 새 ECU를 실행하고, 별도 터미널에서 새 출력 파일명으로 Wireshark의 `vcan0` 캡처를 시작한 뒤 다음을 순서대로 실행합니다. `cansend`(can-utils)가 필요하며 아래 명령 자체는 이번 검증에서 실행하지 않았습니다.

```bash
cansend vcan0 120#1102003C
cansend vcan0 120#12020065
cansend vcan0 120#13010000
```

각 요청의 응답을 확인한 뒤 다음 요청을 보냅니다. 기대 응답은 순서대로 `121#1100003C`, `121#1203003C`, `121#1300003C`입니다. 캡처 종료 후 새 이름으로 PCAPNG를 저장하고 위 필터로 6프레임과 Payload를 확인합니다. ECU는 Ctrl+C로 종료합니다. 기존 원본 캡처와 스크린샷을 덮어쓰지 않습니다.

### 미검증 항목과 한계

- 최종 전체 테스트 실행에 대응하는 PCAPNG/스크린샷은 수집하지 않았습니다.
- ECU 미실행 시 클라이언트 타임아웃, 부하·장시간 동작, 물리 CAN/실제 차량·물리 ECU 시험은 미실시입니다.
- CAN FD·오류 프레임은 vcan 소프트웨어 송신에서의 무응답만 확인했으며 물리 버스의 오류 발생을 검증하지 않았습니다.
- 캡처 중 외부 송신기 부재, 송신 프로세스 신원, 캡처 누락 여부 전체를 독립적으로 보증하지 않습니다. 현재 값은 실습 규격의 설정값이며 차량 물리량 또는 ECU 신호 의미로 해석하지 않습니다.
